아래 회의 녹취록을 읽고 사실에 기반한 상세 회의록을 Markdown으로 작성하세요.

## 가장 중요한 원칙

- 회의록의 최우선 목표는 문장을 예쁘게 쓰는 것이 아니라, **회의에서 나온 핵심 사실을 빠짐없이 보존하는 것**입니다.
- **발언 길이, 반복 횟수, 화자 비중, 설명의 장황함**이 아니라, 아래 항목에 해당하는지를 기준으로 중요도를 판단하세요.
  - 결정사항
  - 미결사항
  - 액션 아이템
  - 일정 / 마감일 / 시점
  - 수치 / 금액 / 목표치 / 범위
  - 리스크 / 우려 / 장애 요인
  - 찬반 의견이 갈린 쟁점
- 짧게 한 번만 언급되었더라도, **결정사항, 담당자, 기한, 숫자, 예산, 리스크**는 반드시 포함하세요.
- **형식보다 정보 보존이 우선**입니다. 출력 형식을 맞추는 과정에서 핵심 사실을 누락하지 마세요.

## 핵심 원칙

- **사실만 기록**: 녹취록에 명시적으로 언급된 내용만 적으세요. 추론·추측·일반론을 절대 추가하지 마세요.
- **빈 섹션 생략**: 해당 내용이 녹취록에 없으면 섹션째 생략하세요. 채우기 위해 지어내지 마세요.
- **명사형 종결 통일**: "~함", "~됨", "~하기로 함", "~논의됨" 형태로 통일. "~합니다", "~했어요" 같은 존댓말·구어체 금지.
- **두괄식**: 각 안건은 결론(결정·결과)을 먼저, 근거·논의 과정을 뒤에.
- **제안과 결정 명확히 구분**: "~하자/~하면 어떨까"(제안)와 "~하기로 했다"(결정)는 다른 카테고리.
- **한 문장 = 한 사실 (단문 원칙)**: 서로 다른 사실·주제를 한 문장에 접속어로 잇지 마세요. 녹취록에 명시되지 않은 인과·순서·조건 관계를 `~하여`, `~함으로써`, `~한 후`, `~통해`, `~하였으며` 같은 연결로 만들어내지 마세요. 관계가 명시되지 않았으면 문장을 나누어 각각 bullet 로 작성하세요. (단, 한 발언 안에서 실제로 언급된 순서·인과는 유지)
- **서술어는 발화 행위에 맞게**: 단순 논의·언급은 `~논의함/~언급함/~공유함`, 검토·미결은 `~검토함/~논의 중임`, 제안은 `~제안함`, 결정은 `~하기로 함/~결정함` 을 쓰세요. `~하기로 함`, `~로 함` 은 녹취록에서 **명시적으로 합의·결정된 경우에만** 사용하고, 단순 논의·제안을 결정처럼 표기하지 마세요.
- **구체적 정보 보존**: 숫자, 날짜, 인명, 금액, 기간, 버전, 지표, 영어 약어(API/KPI/AWS 등)는 변형·생략 금지.
- **짧은 중요 발언 보호**: 짧게 말했더라도 회의 결과에 영향을 주는 발언은 절대 생략하지 않음.

## 전사 오류 처리

이 녹취록은 자동 음성인식(ASR)으로 생성되었으며 인식 오류가 포함될 수 있습니다.
개별 단어의 표면형보다 문맥과 전체 흐름에 집중하되, **핵심 사실을 놓치지 않는 범위에서만** 자연스럽게 교정하세요.

### 고유명사 교정

회사명, 서비스명, 소프트웨어명, 인명 등은 ASR이 한국어 발음대로 잘못 변환하는 경우가 많습니다.
문맥상 충분히 확실할 때만 올바른 영어 원어명으로 교정하세요.
불확실하면 원문 유지 또는 괄호 보조 표시.

교정 예시:
- 깃랩/깃럽/기트랩 → GitLab
- 팔란티어/파란티어 → Palantir
- 퍼플렉시티/퍼픈랩시티 → Perplexity
- 슬랙/슬렉 → Slack
- 노션/노숀 → Notion
- 쿠버네티스/쿠버네틱스 → Kubernetes
- 도커/다커 → Docker
- 피그마/빅마 → Figma
- 젠킨스/젠킨즈 → Jenkins
- 리액트/리엑트 → React
- 타입스크립트/타입스크립 → TypeScript
- 엔비디아/앤비디아 → NVIDIA
- 오픈에이아이/오픈AI → OpenAI
- 마이크로소프트/마소 → Microsoft
- 아마존/아마존웹서비스/에이더블유에스 → AWS

영어 약어(API, KPI, AWS, MAU, DAU 등)는 원어 유지. 음차된 한글 표기 발견 시 영어로 교정.
**고유명사 교정은 회의 핵심 내용 추출보다 우선하지 않습니다.**

### 일반 ASR 오류

- 어색한 띄어쓰기, 조사 오류, 동음이의어 혼동 → 문맥에 맞게 자연스럽게 교정
- 반복/더듬기/필러(아, 음, 그, 어) → 제거하고 의미만 추출
- 문장이 불완전하거나 끊김 → 전후 맥락으로 의도를 파악하여 완성된 문장으로 재구성
- 교정이 불확실하지만 의미 전달이 필요한 경우 → 원문 그대로 + 괄호 표시
- 문맥으로도 의도 파악이 불가능한 경우 → [unclear]

## 작성 절차 (이 순서를 반드시 따를 것)

### 1단계: Coverage Checklist (작성 시작 전, 내부 식별)

회의록을 작성하기 *전에*, 다음을 머릿속으로 빠짐없이 식별합니다.
이 식별은 *주제 단위* 로 진행하며, 화자가 누구든 발화 길이가 짧든 모두 포함합니다.

- 모든 **결정사항**
- 모든 **미결 이슈**
- 모든 **질문 / 우려 / 리스크**
- 모든 **액션 후보**
- 모든 **수치 / 일정 / 금액** 언급
- 모든 **소수의견 / 반대의견**

이 식별 결과는 출력하지 말고, 작성 도중 빠진 항목이 없는지 internal reference 로만 활용합니다.

### 2단계: 주제별 안건 묶기

1단계에서 식별한 항목들을 의미 단위로 묶어 안건으로 재구조화합니다. 시간순이 아닌 주제순.

### 3단계: 회의록 작성

아래 출력 형식에 맞춰 작성. 1단계의 모든 항목이 빠짐없이 반영되어야 함.

### 4단계: Self-Check (출력 직전 자가 검증)

출력하기 직전 다음 체크리스트로 검증:

- ☐ 1단계에서 식별한 모든 결정·미결·액션·수치가 출력에 반영되었는가?
- ☐ 짧게 한 번만 언급된 결정·담당자·기한·숫자가 빠지지 않았는가?
- ☐ 결정(`~하기로 함`)과 제안(`~하면 어떨까`)을 혼동하지 않았는가?
- ☐ 논의·검토에 그친 사항을 `~하기로 함`으로 결정처럼 과장하지 않았는가?
- ☐ 서로 다른 사실을 접속어로 묶어 녹취록에 없는 인과·순서를 만들지 않았는가? (단문 원칙)
- ☐ 소수의견·반대의견이 누락되지 않았는가?
- ☐ "다양한 의견이 논의됨" 같은 일반화 표현이 들어가지 않았는가?
- ☐ 명사형 종결로 일관되게 작성되었는가?

빠진 항목이 있으면 재작성.

## 절대 사용 금지 표현 (Negative Anchor)

다음 표현은 회의록의 가치를 떨어뜨리므로 **절대 사용 금지**:

- "다양한 의견이 논의됨"
- "여러 사항이 검토됨"
- "활발한 토론이 있었음"
- "~에 대해 이야기를 나눔"
- "전반적으로 ~ 분위기였음"
- "심도 있게 논의됨"
- "다각도로 검토됨"

대신: 구체적으로 *어떤* 의견·제안·이슈가 있었는지, *왜* 그렇게 말했는지, *결과는* 어떻게 되었는지를 기록.

## 분량 가이드

각 안건은 다음 floor 를 따를 것:

- 안건당 논의 내용은 **최소 3개 이상의 bullet**, 각 bullet 30자 이상
- 결정·액션만 나열하지 말고, **그 결론에 도달한 과정**(근거·반대의견·검토된 대안)을 1~2 bullet 으로 보존
- 짧게 끝난 안건도 결정·미결·근거를 모두 기록 (생략 금지)
- 회의 분량이 길면 회의록 분량도 비례하여 길어져야 함 — 압축 모드로 들어가지 말 것

## 결정 표기 규칙

각 결정사항은 다음 슬롯을 가능한 만큼 채울 것:

- **결정**: 합의된 사항 (한 줄)
- **근거**: 왜 이 결정인가 (회의에서 명시된 이유)
- **검토된 대안**: 논의되었으나 기각된 옵션 (있을 때만)
- **전제**: 어떤 가정 하에서 유효한가 (있을 때만)

근거·대안·전제가 회의에서 명시되지 않았으면 해당 슬롯은 생략 (지어내지 말 것).

## 하지 말 것

- 녹취록에 언급되지 않은 참석자·담당자·결정·일정·액션을 지어내지 말 것
- 발언량이 많은 사람의 설명을 길게 요약하고 짧게 언급된 핵심 결론을 빼먹지 말 것
- 결론이 나지 않은 안건에 대해 억지로 결론짓지 말 것
- 녹취록에 없는 "담당:", "참석자:" 같은 필드를 임의로 추가하지 말 것
- 화자 라벨을 100% 신뢰해서 잘못된 책임 귀속 만들지 말 것
